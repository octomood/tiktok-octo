# Правила для агентов

Этот файл обязателен для AI-агентов и контрибьюторов, которые меняют
репозиторий. Если правило конфликтует с прямой просьбой пользователя, сначала
уточните конфликт, а не молча выбирайте одну сторону.

## 1. Changelog — часть definition of done

`CHANGELOG.md` читают пользователи: из него же собирается описание релиза на
GitHub. Поэтому запись нужна, когда изменение видно в приложении, и **в том же
изменении, а не отдельным коммитом потом**.

- Правка идёт в раздел текущей версии из `package.json`, а если после
  версионного раздела уже заведён `## Не выпущено` — в него.
- Секции: `### Добавлено`, `### Изменено`, `### Исправлено`, `### Удалено`.
- Формулировки — по-русски, кратко и в терминах пользовательского эффекта:
  что изменилось и зачем. Внутренние подробности — только если они помогают
  понять изменение.
- Не пишите о внутреннем: тесты, CI, сборка и её артефакты, скрипты для
  разработчика, `AGENTS.md`, `opencode.json`, служебные правки в `docs/`. Такое
  остаётся в ответе пользователю и в сообщении коммита, а не в changelog.
- Указывайте затронутые разрешения, настройки, файлы или тесты, когда это
  важно для проверки.
- Не переписывайте и не удаляйте чужие записи без необходимости. Дополняйте
  существующие пункты, если изменение логически продолжает их.
- Не создавайте новый раздел версии и не меняйте версию в `package.json` без
  явной просьбы.
- Изменение с видимым для пользователя эффектом без записи в changelog
  считается незавершённым.

Шаблон:

```md
- **Короткое название** — что изменилось для пользователя. Если нужно:
  где это видно, какое разрешение/настройка задействованы, какой тест
  покрывает.
```

## 2. Спрашивайте, когда решение за пользователем

Лучше один вопрос до работы, чем готовая фича не с тем поведением.

- Спрашивайте, если у задачи несколько равнозначных вариантов (UX, название,
  место в интерфейсе, значение настройки по умолчанию); если нужно менять
  публичное API плагинов, разрешения или безопасность; если речь о данных
  пользователя — удаление, переименование, миграция; если непонятно, что
  считается готовым, или просьба допускает разное чтение.
- Формат — короткий вопрос с вариантами: 2–3 штуки, у первого пометка
  «рекомендую» и объяснение последствий. Без простыней и без «как вам удобнее»
  вместо конкретики.
- Не спрашивайте о том, что написано в правилах или проверяется по коду и
  тестам: сначала посмотрите сами. Один смысловой вопрос за раз, остальное
  решайте и фиксируйте решение в ответе.

## 3. Документация

- Пользовательское поведение, UX, настройки и ограничения — обновляйте
  `README.ru.md` и `README.md` (английское зеркало).
- API плагинов, разрешения и правила публикации — `docs/plugins/` и
  `docs/plugins/PUBLISHING.md`; после правок запускайте `npm run docs:build`.
- Новый метод `octo.*` или новое разрешение — это одна задача в трёх местах:
  код, документация в `docs/plugins/README.md` и тест. `npm run docs:build`
  собирает встроенные доки в `src/renderer/plugins-docs/` (в коммит не идёт),
  поэтому без пересборки менеджер плагинов покажет устаревшее API.
- Не обещайте в документации то, чего нет в коде, и явно фиксируйте
  ограничения (например, что стикер уходит как обычное фото).

## 4. Тесты и проверки

- Новая функциональность и исправления поведения — добавляйте или обновляйте
  Playwright-тест в `test/`.
- Если тест объективно невозможен (например, нативный диалог), объясните это в
  ответе и покройте ближайшую доступную часть.
- Перед завершением запускайте:

```bash
npm run lint
npm test
npx prettier --check <изменённые файлы>
```

- Форматирование всего репозитория может затронуть чужие незакоммиченные
  файлы. Проверяйте формат точечно по своим файлам.
- Тесты не должны ходить в сеть: реальный TikTok, каталог плагинов и
  автообновление подменяются моками или локальными файлами. Иначе тест
  падает из-за чужого сайта, а не из-за правки.
- `npm test` сам уходит под `Xvfb` (`scripts/run-tests.js`), поэтому окна
  Electron не появляются на вашем экране. Не вызывайте `npx playwright test`
  напрямую и не оборачивайте `npm test` в `xvfb-run` — обёртка уже внутри.
- `test-results/`, `playwright-report/`, `dist/` и `src/renderer/plugins-docs/`
  — сгенерированное; не добавляйте их в коммит даже через `git add -f`.

## 5. Архитектура и безопасность

- Не добавляйте приватные API TikTok, обход подписей, scraping cookies и
  прочие способы обойти защиту сайта.
- Плагины остаются в песочнице: без Node, файловой системы и прямой сети;
  доступ только через `window.octo` и разрешения из манифеста.
- Не логируйте токены, cookies, содержимое чатов и другие приватные данные.
- Не ослабляйте CSP, `contextIsolation`, `sandbox` и проверки навигации без
  явной необходимости и объяснения в changelog.
- Сохраняйте чужие незакоммиченные изменения: правьте точечно, не переписывайте
  файлы целиком без причины.
- Новые зависимости — только когда без них нельзя, с обоснованием в ответе и
  `package-lock.json` в том же изменении. Не обновляйте пакеты «заодно» и не
  запускайте `npm audit fix --force`: это ломает Electron и сборку.
- Ключи подписи плагинов (`.octo-keys/`) и системные файлы (`~/.config`,
  `~/.local/share`) не читайте, не копируйте и не коммитьте без явной просьбы.

## 6. Стиль кода

- Main-процесс: CommonJS, `'use strict'`, 2 пробела, одинарные кавычки,
  висячие запятые, ширина 100.
- Renderer: классический скрипт без Node, только `window.octo` и DOM.
- Пользовательские строки интерфейса — по-русски; английский README — зеркало
  русского, а не отдельный продукт.
- Следуйте структуре и именованию соседних модулей.
- Держите дифф минимальным: не переформатируйте и не переименовывайте соседний
  код, не трогайте строки, к которым задача не относится.

## 7. Локализация интерфейса

- Новая строка интерфейса — это ключ (русский текст) плюс переводы во всех
  `src/main/locales/*.json`. Без перевода язык покажет русский текст.
- В renderer не хардкодьте видимый текст: строки идут через словарь
  локализации, шаблоны с числами и именами — вида «Плагин «{0}» включён».
- Арабский требует RTL: проверяйте, что новые элементы не ломают раскладку.
- Переводы плагинов и страниц TikTok — отдельная тема, не путайте с
  локализацией оболочки.

## 8. Коммиты и git

- Сообщения — по-русски, формат `Область: короткое описание`, как в истории:
  `AUR: …`, `Тесты стикеров: …`, `0.5.2: …`. Одна логическая правка — один
  коммит.
- Не коммитьте по своей инициативе: коммит, amend и пуш — только по просьбе.
- Не переписывайте историю: никаких `--amend`, `rebase`, `push --force` для
  чужих коммитов.
- Не откатывайте и не удаляйте чужие правки: `git checkout --`, `git restore`,
  `git clean`, `git reset --hard` — только для своих изменений и с пониманием,
  что там нет чужой работы. Перед правкой смотрите `git status`.

## 9. Публикация и версии — только по просьбе

Релиз на GitHub делает пользователь, а не агент.

- Публикация новой версии — это `git push` тега `v*`, `npm run release`,
  `electron-builder --publish always` и любые другие команды, которые создают
  тег, GitHub Release, артефакты или обновляют `latest*.yml`. Всё это
  выполняется **только после явной просьбы пользователя именно про эту
  версию**. Просьба «сделай фичу» или «поправь баг» разрешением на релиз не
  является.
- Не создавайте теги, не пушьте теги и не меняйте версию в `package.json` и
  анонсы в `aur/` / `flatpak/` по своей инициативе. Версия и changelog
  готовятся в рабочей копии, публикация ждёт команды.
- Если без релиза проверка невозможна, скажите об этом и остановитесь —
  не публикуйте «чтобы проверить».
- Обычные коммиты и пуш в текущую ветку без тега — тоже только если
  пользователь об этом попросил.

Если пользователь всё-таки просит выпустить версию, порядок такой — от него
зависит страница релиза:

1. Поднять версию в `package.json` и показать её в `CHANGELOG.md` отдельным
   разделом `## X.Y.Z` с секциями.
2. Проверить, что `node scripts/release-notes.js vX.Y.Z` выдаёт этот раздел:
   job `notes` в `release.yml` заполняет описание релиза именно им.
3. Обновить пакеты: `aur/` (в том числе контрольная сумма AppImage) и
   `flatpak/`, если менялись версия или зависимости.
4. `npm run lint`, `npm test`, `prettier --check` по изменённым файлам.
5. Создать тег `vX.Y.Z` и запушить его — дальше сборку и публикацию делает
   GitHub Actions. Локальный `npm run release` нужен только если пользователь
   просит собирать с его машины.

## 10. Работа не должна мешать пользователю

Всё, что агент запускает, работает тихо и в фоне: без окон, без перехвата
фокуса, без интерактивных программ, которые ждут ввода.

- Не открывайте GUI: `npm start`, `npm run dev`, `npx electron` и любые
  приложения с видимым окном — **даже на минуту и даже ради скриншота**. Окна
  на экране пользователя — это уже помеха, а не «проверка». Скриншоты и UI
  проверяйте тестом, а не запуском приложения.
- Проверки запускайте в фоне (`background`), логи пишите в файл и читайте
  оттуда.
- Не оставляйте за собой процессы: после проверки останавливайте dev-серверы,
  Electron и наблюдатели файлов.
- Не устанавливайте пакеты в систему и не меняйте настройки ОС без просьбы;
  зависимости проекта — только `npm ci` / `npm install` в репозитории.
- Тесты не запускайте руками: `npm test` уже уходит под `Xvfb`. Настоящее окно
  — только с `OCTO_TEST_WINDOW=1` и только если пользователь об этом попросил.
- На Wayland одного `Xvfb` мало: Chromium выбирает Wayland по `WAYLAND_DISPLAY`
  и рисует окна на рабочем столе. `npm test` снимает переменную
  (`scripts/run-tests.js`, `playwright.config.js`) — не возвращайте её и не
  запускайте тесты в обход обёртки.
- Запрет технический, а не только на словах: `opencode.json` блокирует
  `npm start`, `npm run dev`, `npx electron`, ручной Playwright любым путём,
  браузеры (`chromium`, `google-chrome`, `firefox`, `brave`), `nohup`/`setsid`
  и запуск сборок из `dist/`. Не обходите его через `sh -c` и не просите
  пользователя снять правило: отказ — это нормальное поведение, UI проверяется
  тестом, а готовая версия отдаётся через `npm run install:local`.
- Если команда может открыть окно, а headless-варианта нет — сначала спросите
  разрешение. Запуск «на секунду, посмотреть» считается нарушением.
- Не запускайте длинные задачи без нужды повторно: сначала смотрите, есть ли
  уже результат в `test-results/` или логах.

## 11. Локальная сборка для проверки

В конце работы пользователь должен найти новую версию в меню приложений, а не
инструкцию «запустите `npm start`».

- `npm run install:local` собирает AppImage из текущего рабочего дерева и
  обновляет пункт «TikTok octo (локальная сборка)» в меню приложений.
  Запускайте её после правок кода, сборки или встроенной документации — это
  часть definition of done.
- Сборка идёт в фоне, ничего не публикует (`--publish never`) и не открывает
  окон. Само приложение после сборки не запускайте: пользователь откроет пункт
  меню сам. Это же и есть способ показать UI — не просите снять запрет на
  `npm start`.
- Запущенный экземпляр держит блокировку и перехватит открытие. Напомните в
  ответе, что перед проверкой нужно закрыть старый, но не закрывайте чужие
  процессы сами.
- Правки, которые не попадают в сборку (`AGENTS.md`, README, changelog),
  пересборки не требуют; тесты и линт для них всё равно нужны.

## 12. Правила дополняют сами агенты

`AGENTS.md` — живой документ, а не памятник.

- Если в работе всплыло повторяющееся требование, которого нет в правилах
  (пользователь поправил, проверка стабильно падает на одном и том же,
  выяснилось ограничение окружения), добавьте короткое правило в подходящий
  раздел **в том же изменении**, где это выяснилось.
- Пишите только то, что реально нужно и проверяемо: одна-две строки в стиле
  соседних пунктов, без пересказа кода и без «на будущее на всякий случай».
- Не дублируйте существующие пункты — дополняйте их. Не удаляйте и не
  переписывайте чужие правила без причины.
- Если правило устарело и мешает (например, ссылается на удалённую команду),
  исправьте его и укажите это в ответе пользователю.
- Правка правил — внутреннее изменение: в `CHANGELOG.md` не попадает (§1).

## 13. Чек-лист и отчёт перед завершением

- [ ] `CHANGELOG.md` обновлён, если изменение видит пользователь.
- [ ] `README.ru.md` / `README.md` и `docs/` обновлены, если изменилось
      поведение или API; новое API плагинов — ещё и `npm run docs:build`.
- [ ] Новые строки интерфейса переведены во всех `src/main/locales/*.json`.
- [ ] Добавлены или обновлены тесты.
- [ ] `npm run lint` проходит.
- [ ] `npm test` проходит.
- [ ] Изменённые файлы проходят `prettier --check`.
- [ ] Новых зависимостей нет, либо они обоснованы и попали в `package-lock.json`.
- [ ] Для правок кода собрана локальная версия (`npm run install:local`).
- [ ] Вопросы, где решение за пользователем, заданы до реализации.
- [ ] Ничего не опубликовано на GitHub и не создано тегов без явной просьбы.
- [ ] После проверок не осталось запущенных процессов и окон.

В ответе пользователю коротко: что изменено и зачем, какие файлы затронуты, что
проверено, что не проверено и почему, нужен ли релиз и обновление changelog. Если
собиралась локальная версия — одной строкой, где открыть её в меню и что старый
экземпляр нужно закрыть.
