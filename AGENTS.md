# Правила для агентов

Этот файл обязателен для AI-агентов и контрибьюторов, которые меняют
репозиторий. Если правило конфликтует с прямой просьбой пользователя, сначала
уточните конфликт, а не молча выбирайте одну сторону.

## 1. Changelog — часть definition of done

`CHANGELOG.md` читают пользователи: из него же собирается описание релиза на
GitHub. Поэтому запись нужна, когда изменение видно в приложении, и **в том же
изменении, а не отдельным коммитом потом**.

- Проверьте, выпущена ли текущая версия из `package.json` (есть ли тег
  `v<версия>` в `git tag`):
  - Если уже заведён `## Не выпущено` или тег `v<версия>` уже существует
    (версия релизнулась), **не дописывайте в выпущенный раздел `## <версия>`**
    — пишите в `## Не выпущено` вверху `CHANGELOG.md` (создайте этот раздел
    над последним выпущенным релизом, если его ещё нет).
  - Если тега `v<версия>` ещё нет и `## Не выпущено` не заведён, пишите в
    раздел текущей версии из `package.json`.
- Секции: `### Добавлено`, `### Изменено`, `### Исправлено`, `### Удалено`.
- Формулировки — по-русски, кратко и в терминах пользовательского эффекта:
  что изменилось и зачем. Внутренние подробности — только если они помогают
  понять изменение.
- Пункт — одна-две строки, максимум три. Длинные объяснения причин и устройства,
  имена тестов и внутренних файлов в описание релиза не выносите.
- Не пишите о внутреннем: тесты, CI, сборка и её артефакты, скрипты для
  разработчика, `AGENTS.md`, `opencode.json`, служебные правки в `docs/`, промо
  (ролики, обложки, посты в каналы, ассеты `docs/promo/`). Такое остаётся в
  ответе пользователю и в сообщении коммита, а не в changelog и не в описании
  релиза на GitHub: пользователю эти подробности не нужны.
- Указывайте затронутые разрешения и настройки, когда это важно для проверки.
- Не переписывайте и не удаляйте чужие записи без необходимости. Дополняйте
  существующие пункты, если изменение логически продолжает их.
- Не создавайте новый номерной раздел версии (`## X.Y.Z`) и не меняйте версию в
  `package.json` без явной просьбы — для изменений после уже выпущенного
  релиза используйте только `## Не выпущено`.
- **Плагины — не часть релиза приложения.** Официальные плагины из `plugins/`
  (`gradient-frame`, `shelf` и другие) выпускаются своей версией: `version` и
  `changelog` в `plugin.json`, пакет в `plugins/packages/`, запись в канале.
  Они не привязаны к версии и тегу приложения и не попадают в `CHANGELOG.md`
  отдельными пунктами. В changelog идут только оболочка и система плагинов
  (API `octo.*`, разрешения, менеджер), а изменения самого плагина — в его
  собственном changelog.
- Изменение с видимым для пользователя эффектом без записи в changelog
  считается незавершённым; исключение — правки официальных плагинов, у них
  свой changelog.

Шаблон:

```md
- **Короткое название** — что изменилось для пользователя. Если нужно:
  где это видно, какое разрешение/настройка задействованы, какой тест
  покрывает.
```

## 2. Спрашивайте, когда решение за пользователем

Лучше один вопрос до работы, чем готовая фича не с тем поведением.

- Спрашивайте, если у задачи несколько равнозначных вариантов (UX, название,
  место в интерфейсе, значение настройки по умолчанию); если нужно менять
  публичное API плагинов, разрешения или безопасность; если речь о данных
  пользователя — удаление, переименование, миграция; если непонятно, что
  считается готовым, или просьба допускает разное чтение.
- Формат — короткий вопрос с вариантами: 2–3 штуки, у первого пометка
  «рекомендую» и объяснение последствий. Без простыней и без «как вам удобнее»
  вместо конкретики.
- Не спрашивайте о том, что написано в правилах или проверяется по коду и
  тестам: сначала посмотрите сами. Один смысловой вопрос за раз, остальное
  решайте и фиксируйте решение в ответе.

## 3. Документация

- Пользовательское поведение, UX, настройки и ограничения — обновляйте
  `README.ru.md` и `README.md` (английское зеркало).
- API плагинов, разрешения и правила публикации — `docs/plugins/` и
  `docs/plugins/PUBLISHING.md`; после правок запускайте `npm run docs:build`.
- Новый метод `octo.*` или новое разрешение — это одна задача в трёх местах:
  код, документация в `docs/plugins/README.md` и тест. `npm run docs:build`
  собирает встроенные доки в `src/renderer/plugins-docs/` (в коммит не идёт),
  поэтому без пересборки менеджер плагинов покажет устаревшее API.
- Не обещайте в документации то, чего нет в коде, и явно фиксируйте
  ограничения (например, что стикер уходит как обычное фото).

## 4. Тесты и проверки

- Не пишите бесполезные и лишние тесты ради галочки: добавляйте или обновляйте
  тест только тогда, когда изменилась реальная логика или поведение, которое
  может сломаться и ещё не покрыто. Не создавайте тесты на тривиальные вещи
  (наличие файла, статический JSON/текст, CSS на нарисованной вручную заглушке
  без логики) и не дублируйте уже существующие сценарии; чистую логику без
  Electron/DOM проверяйте обычным unit-тестом без `electron.launch`.
- Если тест объективно невозможен (например, нативный диалог), объясните это в
  ответе и покройте ближайшую доступную часть.
- **Проверяйте только то, что сделали и затронули именно вы**, а не всё
  подряд. Запускайте точечно свой тест или затронутый spec (или `-g "..."`)
  через обёртку:

```bash
npm run lint
npm test -- test/<свой-или-затронутый>.spec.js
npx prettier --check <изменённые файлы>
```

- Полный `npm test` без фильтра запускайте **только** при релизе (§9), при
  правках общего ядра/инфраструктуры, влияющих на всё приложение (например,
  запуск окна, preload, store, `run-tests.js`), или по прямой просьбе
  пользователя.
- Если правка не меняет исполняемый код (только `AGENTS.md`, `README*.md`,
  `CHANGELOG.md`, `badges.json`, promo-видео и т. п.), Playwright-тесты вообще не
  запускайте — достаточно `npx prettier --check <изменённые файлы>` и проверки
  формата (например, валидности JSON).

- Форматирование всего репозитория может затронуть чужие незакоммиченные
  файлы. Проверяйте формат точечно по своим файлам.
- Тесты не должны ходить в сеть: реальный TikTok, каталог плагинов и
  автообновление подменяются моками или локальными файлами. Иначе тест
  падает из-за чужого сайта, а не из-за правки.
- `npm test` сам уходит под `Xvfb` (`scripts/run-tests.js`), поэтому окна
  Electron не появляются на вашем экране. Не вызывайте `npx playwright test`
  напрямую и не оборачивайте `npm test` в `xvfb-run` — обёртка уже внутри.
- Одноразовые экраны первого запуска в тестах по умолчанию выключены: каждый
  сценарий стартует с пустым профилем, и такой экран перекрыл бы полосу и
  панель. Проверяйте их отдельно, включая явным флагом (`OCTO_WELCOME=1`).
- `test-results/`, `playwright-report/`, `dist/` и `src/renderer/plugins-docs/`
  — сгенерированное; не добавляйте их в коммит даже через `git add -f`.

## 5. Архитектура и безопасность

- Не добавляйте приватные API TikTok, обход подписей, scraping cookies и
  прочие способы обойти защиту сайта.
- Плагины остаются в песочнице: без Node, файловой системы и прямой сети;
  доступ только через `window.octo` и разрешения из манифеста.
- Не логируйте токены, cookies, содержимое чатов и другие приватные данные.
- Не ослабляйте CSP, `contextIsolation`, `sandbox` и проверки навигации без
  явной необходимости и объяснения в changelog.
- Сохраняйте чужие незакоммиченные изменения: правьте точечно, не переписывайте
  файлы целиком без причины.
- Новые зависимости — только когда без них нельзя, с обоснованием в ответе и
  `package-lock.json` в том же изменении. Не обновляйте пакеты «заодно» и не
  запускайте `npm audit fix --force`: это ломает Electron и сборку.
- Ключи подписи плагинов (`.octo-keys/`) и системные файлы (`~/.config`,
  `~/.local/share`) не читайте, не копируйте и не коммитьте без явной просьбы.
  Исключение — токен описаний релизов из §9: его читают только для этой задачи.

## 6. Стиль кода

- Main-процесс: CommonJS, `'use strict'`, 2 пробела, одинарные кавычки,
  висячие запятые, ширина 100.
- Renderer: классический скрипт без Node, только `window.octo` и DOM.
- Пользовательские строки интерфейса — по-русски; английский README — зеркало
  русского, а не отдельный продукт.
- Следуйте структуре и именованию соседних модулей.
- Держите дифф минимальным: не переформатируйте и не переименовывайте соседний
  код, не трогайте строки, к которым задача не относится.

## 7. Локализация интерфейса

- Новая строка интерфейса — это ключ (русский текст) плюс переводы во всех
  `src/main/locales/*.json`. Без перевода язык покажет русский текст.
- В renderer не хардкодьте видимый текст: строки идут через словарь
  локализации, шаблоны с числами и именами — вида «Плагин «{0}» включён».
- Арабский требует RTL: проверяйте, что новые элементы не ломают раскладку.
- Переводы плагинов и страниц TikTok — отдельная тема, не путайте с
  локализацией оболочки.

## 8. Коммиты и git

- Сообщения — по-русски, формат `Область: короткое описание`, как в истории:
  `AUR: …`, `Тесты стикеров: …`, `0.5.2: …`. Одна логическая правка — один
  коммит.
- Не коммитьте по своей инициативе: коммит, amend и пуш — только по просьбе.
- Не переписывайте историю: никаких `--amend`, `rebase`, `push --force` для
  чужих коммитов.
- Не откатывайте и не удаляйте чужие правки: `git checkout --`, `git restore`,
  `git clean`, `git reset --hard` — только для своих изменений и с пониманием,
  что там нет чужой работы. Перед правкой смотрите `git status`.
- После любого `git push` (ветки или тега) обязательно отслеживайте статус
  GitHub Actions (`https://api.github.com/repos/octomood/tiktok-octo/actions/runs`)
  до полного завершения всех проверок. Если какой-то workflow или тест упал —
  разберите ошибку, исправьте её, перепроверьте локально, снова запушьте и
  дождитесь зелёного результата, и только после этого сообщайте о готовой работе.

## 9. Публикация и версии — только по просьбе

Релиз на GitHub делает пользователь, а не агент.

- Публикация новой версии — это `git push` тега `v*`, `npm run release`,
  `electron-builder --publish always` и любые другие команды, которые создают
  тег, GitHub Release, артефакты или обновляют `latest*.yml`. Всё это
  выполняется **только после явной просьбы пользователя именно про эту
  версию**. Просьба «сделай фичу» или «поправь баг» разрешением на релиз не
  является.
- Не создавайте теги, не пушьте теги и не меняйте версию в `package.json` и
  анонсы в `aur/` / `flatpak/` по своей инициативе. Версия и changelog
  готовятся в рабочей копии, публикация ждёт команды.
- Если без релиза проверка невозможна, скажите об этом и остановитесь —
  не публикуйте «чтобы проверить».
- Обычные коммиты и пуш в текущую ветку без тега — тоже только если
  пользователь об этом попросил.
- Выпуск официального плагина — не релиз приложения: версия поднимается в его
  `plugin.json`, пакет собирается в `plugins/packages/`, запись уходит в канал.
  Не поднимайте из-за этого версию в `package.json`, не создавайте тег `v*` и
  не добавляйте пункт в `CHANGELOG.md`.
- Токен для правки описаний релизов лежит вне репозитория:
  `~/.config/tiktok-octo/github-token` (права `0600`). Используйте его только для
  запросов к `api.github.com/repos/octomood/tiktok-octo/releases`; не печатайте
  токен, не копируйте в репозиторий и не коммитьте. Описание релиза правьте
  только когда об этом просит пользователь, и держите его синхронным с
  `CHANGELOG.md`.

Если пользователь всё-таки просит выпустить версию, порядок такой — от него
зависит страница релиза:

1. Поднять версию в `package.json` и переименовать `## Не выпущено` в
   `CHANGELOG.md` в `## X.Y.Z` (или завести новый раздел `## X.Y.Z` с секциями,
   если `## Не выпущено` не было).
2. Проверить, что `node scripts/release-notes.js vX.Y.Z` выдаёт этот раздел:
   job `notes` в `release.yml` заполняет описание релиза именно им.
3. Обновить пакеты: `aur/` (в том числе контрольная сумма AppImage) и
   `flatpak/`, если менялись версия или зависимости.
4. `npm run lint`, `npm test`, `prettier --check` по изменённым файлам.
5. Создать тег `vX.Y.Z` и запушить его — дальше сборку и публикацию делает
   GitHub Actions. Локальный `npm run release` нужен только если пользователь
   просит собирать с его машины.

## 10. Работа не должна мешать пользователю

Всё, что агент запускает, работает тихо и в фоне: без окон, без перехвата
фокуса, без интерактивных программ, которые ждут ввода.

- Не открывайте GUI: `npm start`, `npm run dev`, `npx electron` и любые
  приложения с видимым окном — **даже на минуту и даже ради скриншота**. Окна
  на экране пользователя — это уже помеха, а не «проверка». Скриншоты и UI
  проверяйте тестом, а не запуском приложения.
- Проверки запускайте в фоне (`background`), логи пишите в файл и читайте
  оттуда.
- Не оставляйте за собой процессы: после проверки останавливайте dev-серверы,
  Electron и наблюдатели файлов.
- Не устанавливайте пакеты в систему и не меняйте настройки ОС без просьбы;
  зависимости проекта — только `npm ci` / `npm install` в репозитории.
- Тесты не запускайте руками: `npm test` уже уходит под `Xvfb`. Настоящее окно
  — только с `OCTO_TEST_WINDOW=1` и только если пользователь об этом попросил.
- На Wayland одного `Xvfb` мало: Chromium выбирает Wayland по `WAYLAND_DISPLAY`
  и рисует окна на рабочем столе. `npm test` снимает переменную
  (`scripts/run-tests.js`, `playwright.config.js`) — не возвращайте её и не
  запускайте тесты в обход обёртки.
- Запрет технический, а не только на словах: `opencode.json` блокирует
  `npm start`, `npm run dev`, `npx electron`, ручной Playwright любым путём,
  браузеры (`chromium`, `google-chrome`, `firefox`, `brave`), `nohup`/`setsid`
  и запуск сборок из `dist/`. Не обходите его через `sh -c` и не просите
  пользователя снять правило: отказ — это нормальное поведение, UI проверяется
  тестом, а готовая версия отдаётся через `npm run install:local`.
- Если команда может открыть окно, а headless-варианта нет — сначала спросите
  разрешение. Запуск «на секунду, посмотреть» считается нарушением.
- Не запускайте длинные задачи без нужды повторно: сначала смотрите, есть ли
  уже результат в `test-results/` или логах.

## 11. Локальная сборка для проверки

В конце работы пользователь должен найти новую версию в меню приложений, а не
инструкцию «запустите `npm start`».

- `npm run install:local` собирает AppImage из текущего рабочего дерева и
  обновляет пункт «TikTok octo (локальная сборка)» в меню приложений.
  Запускайте её после правок кода, сборки или встроенной документации — это
  часть definition of done.
- Сборка идёт в фоне, ничего не публикует (`--publish never`) и не открывает
  окон. Само приложение после сборки не запускайте: пользователь откроет пункт
  меню сам. Это же и есть способ показать UI — не просите снять запрет на
  `npm start`.
- Запущенный экземпляр держит блокировку и перехватит открытие. Напомните в
  ответе, что перед проверкой нужно закрыть старый, но не закрывайте чужие
  процессы сами.
- Правки, которые не попадают в сборку (`AGENTS.md`, README, changelog),
  пересборки и прогона Playwright-тестов не требуют — достаточно
  `npx prettier --check <изменённые файлы>`.

## 12. Правила дополняют сами агенты

`AGENTS.md` — живой документ, а не памятник.

- Если в работе всплыло повторяющееся требование, которого нет в правилах
  (пользователь поправил, проверка стабильно падает на одном и том же,
  выяснилось ограничение окружения), добавьте короткое правило в подходящий
  раздел **в том же изменении**, где это выяснилось.
- Пишите только то, что реально нужно и проверяемо: одна-две строки в стиле
  соседних пунктов, без пересказа кода и без «на будущее на всякий случай».
- Не дублируйте существующие пункты — дополняйте их. Не удаляйте и не
  переписывайте чужие правила без причины.
- Если правило устарело и мешает (например, ссылается на удалённую команду),
  исправьте его и укажите это в ответе пользователю.
- Правка правил — внутреннее изменение: в `CHANGELOG.md` не попадает (§1).

## 13. Чек-лист и отчёт перед завершением

## 15. Видео и промо

- Ролик — это код и ассеты, а не ручной монтаж. Кадры считает сцена с
  `window.renderAt(t)`, звук — Python-синтез; всё должно пересобираться одной
  командой `bash docs/promo/build-*.sh`. Экспорт из видеоредактора в репозиторий
  не кладём: его нельзя проверить и воспроизвести.
- Новый ролик — новый файл `tiktok-octo-<тема>-<секунды>s.mp4` и обложка
  `<тема>-<секунды>s.png`. Существующие промо не перезаписывайте без прямой
  просьбы: рядом со старым роликом проще сравнить.
- Формат по умолчанию — вертикаль 1080×1920, 30 к/с, H.264 High, `yuv420p`,
  bt709, AAC 192 кбит/с 48 кГц, `-movflags +faststart`, ровно заявленная
  длительность. 16:9 — только для сайта или канала.
- Держите безопасные зоны: интерфейс TikTok закрывает низ и правый край. Текст,
  QR и важные детали — в пределах примерно 60…1020 px по X и до 1700 px по Y;
  нижние 250–300 px оставляйте пустыми.
- Сцена детерминирована: состояние — чистая функция `t`, без CSS-переходов и
  анимаций; один `t` всегда даёт один кадр. `window.DUR` задаёт длительность,
  `render.mjs --scene <файл>` — рендер.
- Перед полным рендером смотрите stills ключевых моментов и все склейки. Первый
  кадр новой сцены должен уже содержать контент: чёрные или серые кадры на
  стыке — брак, а не «стильная пауза», если их больше одного-двух.
- Шрифты, эмодзи и картинки — только локальные: `src/renderer/fonts.css`,
  системный `Noto Color Emoji`, `docs/promo/assets/`. Никаких веб-шрифтов,
  CDN, чужих мемов, стоковых видео и музыкальных сэмплов: рендер обязан
  работать офлайн, а звук синтезируется.
- Звук: цель около −14 LUFS (допустимо −13…−15), пик не выше −1 dBFS.
  Проверяйте `ffmpeg -af ebur128=peak=true` и RMS по секундам: пауза перед
  ударом — приём, случайный провал — брак.
- Шутки не выдумывают функций. Хоткеи, разрешения, «проверено», «open source»,
  «без регистрации» сверяйте с кодом и README. Мемность — это монтаж, крупный
  текст, эмодзи, штампы и знакомые ситуации, а не выдуманные факты.
- После сборки проверяйте `ffprobe` (длительность, число кадров, разрешение,
  звук), а QR — `zbarimg` по кадру из готового mp4, не по исходнику.
- Каталоги `build-*/` и промежуточные кадры — сгенерированное: добавьте их в
  `docs/promo/.gitignore`, в коммит не берите. Готовые mp4 и обложки — можно.
- Полный рендер 24 секунд при `--dsf 2` идёт 5–7 минут: запускайте в фоне, лог —
  в файл, без плеера и окон (§10). Не пересобирайте без причины.
- В `docs/promo/README.md` обновляйте таймлайн, команду сборки, состав файлов и
  реальные цифры (длительность, LUFS). В `CHANGELOG.md` и описание релиза промо
  не попадает (§1).
- Playwright-тест для самого mp4 не нужен; проверка — сборка, stills,
  `ffprobe`, `zbarimg` и `npx prettier --check <изменённые файлы>` (а
  `npm run lint` — только если менялись JS-скрипты). Общий `npm test` не
  запускайте.
- Подробный порядок и грабли — в `docs/promo/README.md`, раздел «Порядок
  работы для агента».

## 16. Дизайн и интерфейс (Material Design 3 Expressive)

Все элементы оболочки, дочерних окон и скина сайта оформляются по единым
правилам MD3 Expressive; новые компоненты и правки не должны от них отходить.

- **Токены и 20 палитр**: цвета задаются только через переменные `--md-*` в
  оболочке и `--octo-md-*` в [md3-site.js](src/main/md3-site.js) (источник —
  [md3-palettes.js](src/main/md3-palettes.js)). Никаких жёстких `#hex`,
  розовых/бирюзовых акцентов TikTok (`#fe2c55`, `#25f4ee`, бордового
  `disabled`-фона) и тёмной заливки без учёта светлой темы.
- **Сгруппированные списки и карточки** (Настройки, сайдбар, меню):
  - Пункты группы видимы по умолчанию (`--md-surface-container` на подложке
    `--md-surface-container-low`), а при `:hover` становятся чуть ярче
    (`--md-surface-container-high`).
  - Зазор между пунктами внутри группы — `4px`, между группами — отдельный
    отступ с заголовком группы.
  - Внешние края группы скругляются умеренно (`14px`–`16px` сверху у первого и
    снизу у последнего, у одиночного — со всех сторон), внутренние углы и
    пункты в центре остаются малоскруглёнными (`6px`). **Не ставьте**
    `border-radius: 9999px` на `:hover` невыбранных строк и не переписывайте
    только одну сторону углов без учёта противоположной — при CSS-нормализации
    радиусов верх и низ меняются местами.
  - Активный выбранный пункт навигации или опция списка выделяется капсулой
    `border-radius: 9999px` (`--md-secondary-container` /
    `--md-on-secondary-container`).
- **Кнопки, чипы, переключатели и поля ввода**:
  - Одиночные акцентные и тональные кнопки — пилюли `9999px`; связанные группы
    кнопок имеют внешние края `9999px`, внутренние `6px` (`12px` на `:hover`) и
    зазор `2px`–`4px`.
  - Горизонтальные фильтры и категории (вне вкладок `[role="tablist"]` с
    нижней линией) оформляются отдельными pill-чипами `9999px`, без
    состыкованных прямоугольников `5px` и видимых скроллбаров под лентой.
  - В полях ввода (включая модалки TikTok и поиск) фон, рамка и `border-radius`
    задаются **ровно одному** внешнему контейнеру, а внутренний `<input>` и
    промежуточные `div` очищаются (`transparent`, `border: 0`, `border-radius: 0`),
    чтобы по краям не появлялись вырезы-«скобки».
  - Отключённые кнопки (`:disabled`, `[aria-disabled="true"]`) получают
    нейтральный MD3-контейнер вместо полупрозрачного красного.
- **Выпадающие списки (`<select>`)**:
  - В оболочке нативные системные popup-списки `<select>` заменяются общим
    компонентом [md3-select.js](src/renderer/md3-select.js), при этом сам
    `<select>` остаётся в DOM прозрачным ради доступности и `selectOption(...)`
    в тестах. В [md3-site.js](src/main/md3-site.js) используется прогрессивный
    `appearance: base-select` и `::picker(select)` в палитре темы.
- **Пружины, компактные рельсы и проверка охватов**:
  - Для `transform` можно использовать пружины `--md-spring-spatial-*`, а для
    `border-radius` при переходе к пилюле — **только** монотонную кривую
    `--md-shape-ease` (`cubic-bezier(0.2, 0, 0, 1)`) и реальный pill-радиус
    `--md-shape-pill` (`24px`), а не `9999px` и не кривые с перелётом `y > 1`:
    иначе при переходе `9999px → 6px` углы проваливаются в `0px` (острые).
    Для цвета и прозрачности используйте `--md-spring-effects-*`, сохраняя
    поддержку `prefers-reduced-motion: reduce`.
  - Узкие боковые панели (`< 120px`) переходят в центрированные плитки
    `44×44` без рамок вокруг иконок и без обрезания подписей кнопок.
  - После правок UI проверяйте не только главную ленту и «Настройки», но и
    сайдбар (широкий/узкий), шторки («Ещё», «Уведомления»), профиль, «Смотреть»,
    «Мини-сериалы», `/setting`, модалки авторизации и выпадающие меню.

## 17. Бейджи сообщества у ников (`src/main/badges.json`)

Когда пользователь просит выдать, изменить или снять значок (бейдж) возле
ника в клиенте:

- Редактируйте только [`src/main/badges.json`](src/main/badges.json):
  предустановленные роли — в `roles`, конкретные пользователи — в `users`.
- Ключ в `users` — TikTok-ник в нижнем регистре **без `@`** (например,
  `churros_dev`). Не выдумывайте ники, причины и описания: берите их из
  просьбы пользователя; если ник или текст описания не указаны — уточните.
- Формат записи пользователя (один объект или массив объектов для нескольких
  бейджей):
  - `role` _(необязательно)_: `creator`, `dev`, `supporter`, `bug_hunter`,
    `verified` — задаёт значения по умолчанию;
  - `icon`: ID иконки из [`src/main/badge-icons.js`](src/main/badge-icons.js)
    (`01_code_brackets` / `code`, `02_terminal_window` / `terminal`,
    `03_bug_radar` / `bug`, `04_gear_cog` / `gear`, `05_puzzle_module` /
    `puzzle`, `06_rocket_launch` / `rocket`, `07_terminal_bolt` / `bolt`,
    `08_magic_wand` / `wand`, `09_heart_pulse` / `heart`, `10_fire_streak` /
    `fire`, `11_star_shine` / `star`, `12_sparkle_burst` / `sparkles`,
    `13_thumbs_up` / `thumbs-up`, `14_shield_check` / `shield`,
    `15_check_pill` / `check`, `16_alert_triangle` / `alert`,
    `17_bell_notify` / `bell`, `18_chat_typing` / `chat`,
    `19_megaphone_news` / `megaphone`, `20_handshake_collab` / `handshake`);
  - `title` (до 80 символов) и `description` (до 320 символов) — короткий
    заголовок роли и история/благодарность, показываемые в модалке по клику;
  - `accent` (`primary` | `secondary` | `tertiary`) или `color` (`#RRGGBB`,
    опционально — иначе цвет берётся из текущей MD3-палитры пользователя).
- После правок `src/main/badges.json` проверьте валидность JSON и

  `test/user-badges.spec.js` ради одной записи в JSON не нужно (тест бейджей
  запускайте только при правке самой логики бейджей). Новую версию приложения
  в `package.json` ради выдачи бейджа не поднимайте: после коммита/пуша в `main`
  клиенты подтягивают обновлённый `badges.json` с GitHub автоматически.
